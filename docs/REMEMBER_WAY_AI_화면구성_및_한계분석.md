## 1부. 화면 구성

### 1. 전체 구조

웹앱(모바일 폭) 한 페이지, 섹션 5개 전환. 상태는 `case` JSON 하나로 관리.

```
화면 0 평소 등록(선택) ─┐
                        ├─→ 화면 2 확인·되묻기 [AI 핵심] → 화면 3 경찰 전달 요약 → 화면 4 찾은 뒤 기록 [AI 핵심] → (화면 0 갱신)
화면 1 상황 입력 ───────┘
```

화면 0은 건너뛰어도 1~4가 작동한다. 만드는 순서는 **1→2→3 → 0 → 4 → 환자 모드**(10/25 확정).

**축적 방식(10/25 확정): GPS 하드웨어 대신 대화형 일지.** 첫 등록은 한 번 자세히, 이후는 하루 10초(칩 탭). 새 장소나 "가고 싶다" 같은 말이 나올 때만 AI가 구조화한다. 일지에서 장소를 네 종류로 나눈다(코드 규칙, 임계값 공개):

| 분류 | 규칙 (30일 기준) | 가중치 |
|---|---|---|
| 추억 장소 | 첫 등록에 있고 일지엔 드묾 / "가고 싶다"고만 한 곳 | +3 |
| 최근 자주 가기 시작한 곳 | 최근 14일 방문 ≥ 이전 14일 × 2 | +3 |
| 자주 가는 곳 | 30일 중 4회 이상 | +2 |
| 새로운 곳 | 첫 등장 + 2회 이하 | +2 |
| 기타 보호자 입력 | 당일 대화에서만 나온 곳 | +1 |

기록일이 7일 미만이면 "기록이 적어 패턴 신뢰도가 낮습니다"를 표시한다. 말로만 드러나는 신호("옛날 집 가고 싶다")는 GPS가 못 잡고 일지만 잡는다는 것이 이 방식의 근거다(한국일보 사례: "내 집으로 가겠다"며 보따리를 쌈).

### 2. 화면별 구성

| 화면 | 성격 | 보이는 것 | AI가 만든 것 | 코드·규칙 | 보호자가 확인할 것 |
|---|---|---|---|---|---|
| **0 평소 등록·일지** | 선택 | **첫 등록(한 번, 5분)**: 대화로 추억 장소·습관·보행 → **매일 갱신(10초)**: 아는 장소 칩 탭 / [안 나가심] / [다른 곳이 있어요 🎤] / [오늘은 모름] → **주 1회 요약** 문장 | 첫 등록 구조화, 새 장소·언급 추출(호출 ⑤, 말했을 때만), 주간 요약(호출 ⑥) | 칩 탭은 코드가 빈도만 올림. 장소 4분류(추억/자주/최근 증가/새로운)는 코드 규칙. localStorage, 삭제 버튼, 이름 미수집 | 칩 선택, 새 장소 확인 |
| **1 상황 입력** | 실종 직후 | 즉시 신고 안내 [112] → [말로] [글로] → 음성 인식 결과 → [사진(선택)] → [단서 정리하기] | — | 즉시 신고 안내(규칙), STT, 10초 타임아웃 → 서식 모드 | 인식 결과 오류 수정 |
| **2 확인·되묻기** | **AI 핵심** | 마지막·목적지·경로·옷차림·보행·소지품·약·추억 장소 칸, ⚠ 표시, "AI가 묻습니다 (1/3)", [답하기] [모름], [요약 만들기] | 호출 ① 단서 JSON, 호출 ② 되묻기 질문 | 스키마 검사, 원문 대조(환각 ⚠), 등록 정보로 칸 미리 채움 | 칸마다 ✎ 수정, 질문에 답 또는 모름 |
| **3 경찰 전달 요약** | 규칙·지도 | 인상착의 문장, 마지막 지점·경과, 지도(자택→목적지 경로, 교차로 ●, 추억 장소), 항목별 거리·근거, 고정 문구, [문자] [이미지] [경보 문구 복사] | 호출 ③ 인상착의 문장 | 지도 API 실재 확인·경로·교차로·거리, R_max, 순위·확률 없음 | 보내기 전 최종 확인 |
| **4 찾은 뒤 기록** | **AI 핵심** | "어디서 어떻게 찾으셨나요?" → AI 요약 → 예방 계획(초안) → [수정] [저장] → 등록 갱신 chip | 호출 ④ 요약·패턴·예방 계획·갱신 JSON | 재발 위험 체크, 센터 연계 안내 | 계획 수정·승인 |

### 3. 화면 사이 데이터 흐름

| 단계 | 들어오는 것 | 처리 | 나가는 것 |
|---|---|---|---|
| 0 → 2 | 등록 JSON | 코드: 있으면 화면 2 칸 미리 채움 | 등록 chip |
| 1 → 2 | 발화 텍스트(STT) + 사진 + 현재 시각 | 호출 ① 구조화 → 검증(스키마·원문 대조) → 호출 ② 되묻기 | 단서 JSON, ⚠, 질문 3개 |
| 2 → 3 | 보호자 확인 JSON | 호출 ③ 인상착의 · 지도 API(실재·경로·교차로·거리) · R_max | 요약, 지도, 경보 문구 |
| 3 → 4 | 사건 서술 + 2의 JSON | 호출 ④ 요약·패턴·예방 계획 · 재발 체크 | 기록 카드, 갱신 JSON → 화면 0 |

### 4. 스키마 (고정)

```json
{
  "last_seen": {"time": null, "place": null},
  "today_destination": null,
  "route": null,
  "clothing": {"top": null, "bottom": null, "shoes": null, "hat": null},
  "gait": null,
  "items": {"phone": null, "wallet": null, "cane": null},
  "meds": null,
  "dementia_signs": null,
  "memory_places": [],
  "prior_incidents": null,
  "missing": []
}
```
없는 값은 반드시 `null`. `missing[]`에 비어 있는 키 이름을 넣고, 호출 ②는 이 목록만 보고 질문한다.

### 5. 되묻기 규칙 (호출 ② 시스템 프롬프트)

1. 비어 있는 항목 중 수색에 중요한 순서로 최대 3개: 오늘 목적지 → 경로 → 옷차림 → 약·증상 → 소지품 → 이전 실종
2. 목적지를 답하면 다음 질문은 반드시 경로 ("어느 길로 가세요?")
3. "치매세요?" 금지. "요즘 길을 헷갈려 하신 적 있나요?", "드시는 약이 있으세요?"로 돌려 묻기
4. 보호자 말에 없는 사실을 질문에 끼워 넣지 않기 (원문에 없는 "빨간 모자" 금지)
5. 한 번에 한 가지, 한 문장, 존댓말
6. "모름" → 그 항목은 "확인 못 함"으로 두고 다음으로

### 6. 구현 메모

- 호출 순서: ① → 검증 → ②. 답할 때마다 ①만 재실행(원문에 답을 이어 붙임). ③·④는 버튼.
- 환각 대조: 출력의 각 문자열이 원문(+등록 JSON)에 부분 일치하는지 검사. 불일치 → ⚠, 보호자가 지우거나 고침.
- 장애 대응: 10초 타임아웃 → 서식 모드. 서식 모드만으로도 화면 3이 나와야 함.
- 개인정보: 이름 입력란 없음. 사진은 ③ 호출 후 메모리에서 삭제. 등록 JSON은 보호자 기기, 삭제 버튼 필수.
- 실험 모드: 같은 모의 사례를 '서식만' vs '대화'로 넣어 채워진 칸 수·⚠ 수·소요 시간을 자동 기록하는 토글.

## 2부. 최근 연구·뉴스로 본 한계점 분석

2025~2026년 자료를 중심으로, 우리 설계의 각 구간이 어디서 깨질 수 있는지 찾았다. 각 항목은 **한계 → 우리 설계에 미치는 영향 → 대응(설계 반영 / 실험으로 확인 / 발표에서 명시)** 순서다.

### 한계 1. 구조화 추출은 "거의 맞지만 한 군데는 틀린다"

- **근거:** LLMStructBench(2026, 995건 벤치마크). 항목 단위 정확도는 GPT-4o·Gemma3-27B가 F1 0.96까지 나오지만, **문서 전체가 완전히 맞는 비율은 최고 0.52**. 오류의 96~98%가 "틀린 값"(없는 값을 만들거나 다른 값을 넣음)이고, 빈 키 누락은 작은 모델에서만 나타남. 스키마를 프롬프트에 예시와 함께 넣는 방식(P)이 API의 JSON 모드(PJ+)보다 의미 오류가 적었지만 파싱 실패는 많았음.
- **우리에게:** 화면 2의 단서 JSON은 **열 중 다섯은 어딘가 한 칸이 틀린 채** 나온다고 봐야 한다. 그리고 그 오류는 "비어 있음"이 아니라 "그럴듯한 틀린 값"이다. 옷 색이 바뀌거나, 보호자가 말 안 한 소지품이 생긴다.
- **대응:** ① 원문 대조 ⚠는 선택이 아니라 필수. ② 스키마+예시를 프롬프트에 넣고, 동시에 API의 JSON 모드도 켜서 파싱 실패와 의미 오류를 둘 다 줄인다. ③ 비교 실험 지표에 "문서 전체 정확 비율"을 넣고, 50% 수준이 나와도 숨기지 않는다. ④ 발표에서 "AI가 정리한 것을 보호자가 반드시 확인하는 이유"로 이 숫자를 쓴다.

### 한계 2. 음성 인식은 어르신·당황한 말에 약하다

- **근거:** 고령자 음성 ASR 연구(arXiv 2026.4): 한국어 고령자 데이터 VOTE400(75세 이상 104명)에서 미세조정한 Whisper도 **WER 11.6%**(영어 고령자 4.1%). 원인은 느린 속도·잦은 멈춤·불안정한 조음·쉰 목소리, 그리고 고령자 대화 데이터 부족. 경찰관 면담 연구에서도 신고자 발화가 사투리·울먹임을 포함한다고 함.
- **우리에게:** 화면 1의 입력자는 어르신이 아니라 보호자(대개 50~70대 자녀·배우자)이지만, 당황·울먹임·소음(길거리)·사투리(대전)가 겹친다. 열 단어 중 한 단어가 틀리면 "남색"이 "담색", "삼성동"이 "삼선동"이 될 수 있고, 그 오류가 그대로 JSON에 들어간다.
- **대응:** ① 인식 결과를 화면에 바로 보여 주고 고치게 한다(이미 설계). ② 지명·색·숫자는 되묻기에서 **다시 확인**한다("삼성동 맞으세요?"). ③ 글로 쓰기를 동등한 1순위 입력으로 둔다. ④ 실험 때 모의 사례를 **소음 환경·빠른 말·사투리** 조건으로도 읽어 STT 오류율을 따로 기록한다.

### 한계 3. 보호자가 주는 정보 자체가 불완전하다

- **근거:** 목격자 기술(description) 연구는 사람의 인상착의 묘사가 "대체로 맞지만 특정인을 가려낼 만큼 자세하지 않다"고 본다. 한국 경찰관 면담(2025): 신고 가족 10명 중 3명이 치매 증상을 말하지 않고, 일부는 책임을 피하려 사실과 다르게 말함.
- **우리에게:** 입력이 틀리면 AI가 아무리 정확해도 출력이 틀린다. 특히 옷차림은 보호자가 **오늘 아침에 안 봤을** 수 있다. 우리는 "보호자의 기억만으로"를 내세우는데, 그 기억이 약하다는 게 전제의 약점이다.
- **대응:** ① 사진 입력을 "선택"에서 **"있으면 꼭"**으로 올린다. 오늘 옷 사진이 없으면 최근 사진이라도. ② 되묻기에서 "확실하세요?"를 묻고 불확실 답은 ⚠로 남긴다. 확실하지 않은 정보를 확실한 것처럼 전달하는 게 가장 위험하다. ③ 발표에서 "AI는 기억을 만들어 내지 않는다, 꺼내고 정리할 뿐"이라고 선을 긋는다.

### 한계 4. AI 판단에는 편향과 눈치가 있다

- **근거:** 응급 트리아지 LLM 연구(2025): 같은 증상에서 성별·인종 조합에 따라 위급도 점수가 **거의 한 등급** 달랐고(GPT-4o-mini), 모델들은 가장 위급한 등급을 배정하기를 주저함(보정 문제). 추론(chain-of-thought) 프롬프트가 편향을 줄였음. 저자들은 "LLM은 간호사를 돕되 대체하지 않아야 한다"고 결론.
- **우리에게:** 우리는 위험도를 AI가 판정하지 않기로 했지만(규칙 체크리스트), 되묻기 질문의 **순서와 표현**은 AI가 정한다. 보호자의 말투·사투리·호칭에 따라 질문이 달라지거나, 특정 항목을 덜 묻는 편향이 생길 수 있다.
- **대응:** ① 되묻기 우선순위는 규칙 1에 **고정**하고 AI는 문장만 만든다(이미 설계). ② 위험 요소 체크리스트는 끝까지 코드로 둔다. ③ 실험에서 같은 사례를 표준어/사투리/존댓말/반말로 넣어 질문이 달라지는지 본다.

### 한계 5. 보호자는 위기 순간에 AI를 과신하거나 버린다

- **근거:** 돌봄자 대상 AI 챗봇 연구(2025, 16명): 돌봄자들은 출처가 확인되는 정보를 원했고, 챗봇이 **후속 질문을 해 주길** 원했으며, **긴급 상황에서 사람에게 넘기는 경로가 없는 것**을 가장 불안해했다. "AI에게 너무 의지하게 될까" 걱정도 있었음. 다른 연구들은 LLM 챗봇의 정신건강 위해(아첨, 과의존, 위기 오처리)를 지적.
- **우리에게:** 두 방향의 실패가 있다. 과신: 화면 3 지도를 보고 "AI가 거기 있다고 했다"며 다른 곳을 안 찾거나 112를 미룸. 포기: 화면 2에서 질문이 세 개나 나오면 "지금 이럴 때가 아니다"며 앱을 닫음.
- **대응:** ① 112 안내를 **첫 화면 최상단**에, 지도에는 "예측이 아닙니다" 고정 문구(이미 설계). ② 되묻기는 최대 3개, 각 질문에 [모름] 버튼(이미 설계). ③ **화면 2를 건너뛰고 바로 요약**을 만드는 버튼을 추가한다. 빈 칸이 있어도 요약은 나오게. ④ 실험 지표에 "보호자 역할자가 중간에 포기한 횟수"를 넣는다. 이 수치가 높으면 되묻기 수를 2개로 줄인다.

### 한계 6. 수배 자료는 개인정보와 피로 문제가 있다

- **근거:** 경찰 실종경보 문자는 서울만 2021년 66건 → 2023년 654건으로 늘었고, "새벽에 깨운다", "개인정보 유출 아니냐"는 민원이 들어옴. 발송 조건은 보호자 동의·상습 가출 아님·생명 위험·2개 지역 이내로 엄격하고, 시간은 07~21시로 제한. 전문가는 잦은 발송이 피로를 불러 제도 효과를 약화시킬 수 있다고 경고.
- **우리에게:** 화면 3의 "경보 문구 복사"와 향후 모듈 3(수배 자료 생성)은 보호자가 직접 뿌리는 자료를 만든다. 공식 경보보다 기준이 느슨해지면 개인정보 과다 노출과 "실종자 사진이 단체방을 떠도는" 문제를 우리가 만들 수 있다.
- **대응:** ① 경보 문구는 **경찰에 제출하는 용도**로만 만들고, 앱이 직접 발송하지 않는다. ② 공개 수준 3단계(경찰용/지인용/공개용)를 모듈 3 설계에 넣고, 공개용에는 호칭·인상착의만. ③ 찾은 뒤(화면 4)에 "뿌린 자료 회수 안내"를 넣는다. ④ 발표에서 "우리는 경찰 실종경보를 대체하지 않는다"고 명시.

### 한계 7. 평소 등록 정보는 쌓일수록 위험하다

- **근거:** 2026년 1월 발의된 치매관리법 개정안은 위치·개인정보를 "목적 범위 내 최소한"으로, 본인 또는 보호자 동의를 필수로 함. 돌봄자 AI 연구에서도 돌봄 대상자의 식별 정보를 AI에 넣는 것을 꺼려 "유용함 vs 프라이버시"의 긴장이 확인됨.
- **우리에게:** 화면 0이 쌓는 추억 장소·습관·보행·복용 여부는 모아 놓으면 어르신 한 사람의 생활 프로필이다. 서버에 두면 유출 시 피해가 크고, 외부 LLM API로 보내는 순간 제3자에게 전송된다.
- **대응:** ① 등록 JSON은 보호자 기기에만 저장, 삭제 버튼(이미 설계). ② API 호출 시 등록 정보 중 **그 호출에 필요한 항목만** 보낸다(장소명은 보내되 주소는 동 단위). ③ 복용약은 성분이 아닌 "복용 여부·효과"만. ④ 기획안 7쪽에 치매관리법 개정안의 최소 수집 원칙을 인용.

### 한계 8. 우리가 증명할 수 없는 것

- **근거:** 한국일보 GPS 분석은 13건, 경찰관 면담은 16명, 돌봄자 AI 연구는 16명. 우리가 기대는 근거의 표본이 작다. 우리 실험도 모의 사례 5개 × 학생 역할극이다.
- **우리에게:** "발견 시간을 줄인다", "재실종을 막는다", "경찰이 더 빨리 출발한다"는 어느 것도 우리 실험으로 증명되지 않는다. 증명되는 것은 **"같은 모의 사례에서 고정 서식보다 채워진 칸이 많고, 환각이 n건 있었고, 시간이 m초 걸렸다"**뿐이다.
- **대응:** 발표와 탐구기록물에 이 문장을 그대로 쓴다. 효과는 "기대"로, 측정치는 "모의 실험 결과"로 구분한다. 현장 자문자의 의견은 "자문 의견"으로만 쓴다.
