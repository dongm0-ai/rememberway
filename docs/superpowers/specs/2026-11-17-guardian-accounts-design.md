# 보호자 계정 + 탭 3개 (실시간 위치 · 실종자 찾기 · 추억의 장소) — 설계

2026-11-17 · 재설계 (사용자 결정. 기존 "프로필·일지·사건 기록은 기기에만", "이름·연락처 안 받음" 규칙을 바꾼다 — docs 결정표에 기록)

## 왜

한 어르신을 가족 여러 명이 돌본다. 지금은 추억의 장소·프로필·일지·찾은 뒤 기록이 각자 폰 `localStorage`에만 있어 **보호자1이 저장한 추억의 장소를 보호자2가 못 본다.** 실종 때 찾으러 나간 사람이 등록한 사람이 아니면 찾기 흐름이 빈 정보로 돈다. 폰을 바꾸면 다 사라진다.

성공: 보호자1이 가입·어르신 등록 → 가족을 QR로 초대 → 보호자2가 로그인하면 같은 어르신의 실시간 위치·GPS 기록·추억의 장소를 보고, 실종 때 같은 데이터로 찾기 흐름을 쓴다.

## 방식 (검토한 것)

| 방식 | 장단점 | 결정 |
|---|---|---|
| A. 가족 코드 (로그인 없음) | 개인정보 최소, 작음. 코드를 잊으면 복구 불가, 한 사람만 뺄 수 없음 | 제외 (사용자: 계정이 낫다) |
| **B. 보호자 계정 + QR 초대** | 비밀번호 찾기·사람 단위 내보내기·일회용 초대. 이메일 수집, 작업량 큼 | **채택** |
| C. QR로 기기 간 복사 | 함께 보지 못함 | 제외 |

## 목표 / 비목표 / 하면 실패

- 목표: 이메일 로그인(이메일 저장·자동 로그인), 어르신 여러 분, QR 초대, 탭 3개, 기존 기능을 탭 안으로.
- 비목표: 카카오 로그인(다음 단계), 실시간 공동 편집, 관리자 화면.
- 하면 실패: **로그인 화면에서 112가 안 보임.** 이름·집 주소가 서버에 남음. 다른 가족의 데이터가 보임. 본선(11/22) 시연이 깨짐.

## 제약

- npm 패키지 금지, 빌드 없음. Vercel 함수 12개 이미 다 씀 → **새 함수 파일 없음.** 데이터 API는 `api/loc.js`에 action으로 합친다.
- Supabase 이미 연결(`lib/kv.js`, service_role 키, RLS 켜고 정책 없음). 로그인은 Supabase Auth REST(`/auth/v1/...`)를 브라우저에서 `fetch`로 직접 부른다 — anon 키는 공개용이라 `/api/config`로 내려줘도 된다. 서버 함수는 요청의 access token을 `/auth/v1/user`로 확인한 뒤 service_role로 DB를 만진다.
- Supabase 기본 메일 발송은 시간당 몇 통으로 제한된다 → **가입 시 이메일 확인은 끈다**(바로 로그인). 비밀번호 찾기 메일만 쓴다(드묾). 실서비스 때 SMTP 연결.

## 화면

```
로그인: 이메일(저장됨) / 비밀번호 / [로그인] [가입] [비밀번호 찾기] / [초대 QR 찍기]
        맨 위에 항상: "치매 어르신은 즉시 신고 대상입니다. 먼저 112에 전화하세요." [📞 112]
   ↓ 자동 로그인
상단: 어르신 고르기 ▾ (+ 새 어르신 등록)                    ⚙ 설정
탭:   📍 실시간 위치 | 🚨 실종자 찾기 | 📝 추억의 장소
```

- **📍 실시간 위치:** 목걸이 지도(`/track`), 최근 30일 자주 머문 곳(`/gps`), 목걸이 소리로 찾기(`/find`).
- **🚨 실종자 찾기:** 맨 위 112 고정 문구·버튼, 기존 흐름 `/report → /confirm → /summary → /record` 그대로.
- **📝 추억의 장소:** 장소 추가·삭제, 프로필(호칭·사는 동·습관·걸음), 매일 일지(`/diary`), GPS 머문 곳을 추억의 장소로 넣기.
- **⚙ 설정:** 가족 초대 QR, 가족 목록·내보내기, 어르신 폰 연결 코드, 로그아웃(모든 기기 로그아웃), 어르신 데이터 지우기, 탈퇴.
- 기존 화면 규칙(큰 글자, 48px 터치, 존댓말, 고정 문구, 모의 배너) 유지. 탭은 화면 아래 고정, 폰·PC 같은 디자인.

## 로그인

- 이메일 + 비밀번호. **이메일 저장**(기기 `localStorage`, 다음에 미리 채움). **자동 로그인**: Supabase 세션(refresh token)을 기기에 저장, 앱을 열면 갱신. 로그아웃·다른 기기에서 [모든 기기 로그아웃]·브라우저 기록 삭제 때만 다시 로그인.
- **실종자 찾기는 로그인 필요** (사용자 결정: 어르신 데이터가 계정에 있으므로). 대신 로그인 화면 맨 위에 112 고정 문구·버튼. 자동 로그인이라 평소엔 바로 열린다. 서버 장애 때는 이 폰에 마지막으로 받아 둔 사본으로 찾기 흐름이 돈다(AI 장애 시 서식 모드 원칙과 같음).
- 개인정보: 서버에 남는 사람 정보는 **이메일(Supabase Auth)뿐.** 이름·전화번호 안 받음. 어르신은 호칭만.

## 데이터 (Supabase, `docs/supabase.sql`에 추가)

- `elders` (id uuid, label 호칭, device_hash 어르신 폰 연결 코드 해시, created_at, last_seen)
- `elder_members` (elder_id, user_id, role `owner`|`member`, joined_at) — 이 표에 있어야 그 어르신 데이터를 읽고 쓴다.
- `elder_data` (elder_id pk, profile jsonb, diary jsonb, incidents jsonb, updated_at)
- `invites` (token_hash, elder_id, created_by, expires_at, used_at) — QR = 무작위 토큰, **24시간, 한 번만.**
- `loc_events` 그대로 (dev = 어르신 폰 연결 코드 해시 = `elders.device_hash`). 30일 자동 삭제 그대로.

**서버로 가는 것:** 프로필(추억의 장소 이름·근거, 사는 동, 습관, 걸음 메모), 일지, 찾은 뒤 기록.
**기기에만:** 집 주소(어르신별 키), AI 동의, 실종 진행 중 임시값(`rw_clue` 등), 저장한 이메일, 로그인 세션.
**올리기 전에 빼는 것:** 보호자가 말한 원문 전체(utterance), 집 좌표와 같은 점.

## API (`api/loc.js` action 추가, 로그인 필요한 것은 Authorization 헤더)

`me`(내 어르신 목록) · `elder.create` · `data.load` / `data.save`(base `updated_at` 확인, 오래된 저장은 `CONFLICT`) · `invite.create` / `invite.accept` · `members.list` / `members.remove`(owner) · `elder.leave` · `elder.delete`(owner) · `device.reset`(어르신 폰 연결 코드 재발급) · 기존 `latest`/`places`/`clear`는 key 대신 로그인 + elder_id로(어르신 폰 앱의 `push`만 연결 코드로).

- 권한 규칙: 모든 action은 "이 사용자가 이 어르신의 member인가"를 서버에서 확인. owner만 내보내기·어르신 삭제. 초대는 member 누구나.

## 동기화

- 탭을 열면 `data.load` → 기기 사본 갱신 후 그림(서버 응답 전엔 기기 사본으로 먼저 그림).
- 저장하면 기기에 쓰고 `data.save`. 동시에 고쳐 `CONFLICT`면: 일지는 날짜별로 합쳐 다시 저장, 프로필·기록은 "다른 가족이 먼저 고쳤어요" 후 서버 값을 보여 줌.
- 오프라인·서버 실패: 기기 사본으로 동작, 못 올린 변경 표시, 다음에 다시 올림.
- 처음 로그인했을 때 이 폰에 기존 데이터가 있으면: "이 폰의 등록 정보를 새 어르신으로 올릴까요?" (`rw_track` 기존 연결 코드도 그 어르신의 device_hash로).

## 데이터가 사라지는 경우

| 경우 | 결과 |
|---|---|
| owner가 [어르신 데이터 지우기] | 그 어르신의 elder_data·members·invites·loc_events 전부 삭제 |
| member가 [이 어르신에서 빠지기] | 그 사람만 빠짐. 남은 사람이 있으면 데이터 유지 |
| owner가 빠짐, 남은 사람 있음 | 가장 먼저 들어온 member가 owner |
| **마지막 사람**이 빠지거나 탈퇴 | 그 어르신 데이터 전부 삭제 |
| 탈퇴 | 모든 어르신에서 빠짐(위 규칙) + Supabase Auth 계정 삭제 |
| 삭제된 어르신의 폰 앱이 계속 보냄 | `push`가 `410` → 앱은 대기열 비우고 멈추며 "연결이 끊겼어요" 표시 (`TrackerService.kt` 수정, APK 재빌드) |
| 연결 코드 재발급 | 옛 코드 push는 410, 어르신 폰에 새 코드 입력 |

## 설계자 판단 (사용자 확인 대상)

탭에 기존 기능 배치 · 이메일+비밀번호(카카오는 다음) · 가입 시 이메일 확인 끔 · 초대 QR 24시간 1회 · owner/member 두 역할 .

## 검토 후 정한 것

1. **모르는 연결 코드의 push:** `elders`에 없는 코드(이번 변경 전에 만든 코드)는 지금처럼 받는다. `410`은 삭제·재발급으로 폐기된 코드에만 — 폐기한 코드 해시를 `revoked_devices`에 남긴다. 배포 직후 기존 폰·시연 폰이 끊기지 않는다. (설계자 판단)
2. **로그아웃은 아무것도 지우지 않는다** (사용자 결정). 데이터는 계정(서버)에 있고, 다시 로그인하면 그대로. 이 폰의 사본은 화면에서만 감추고 다음 로그인 때 그 계정 것으로 바꾼다 — 다른 계정으로 로그인하면 이전 계정 사본은 지운다(서버 데이터는 그대로).
3. **자동 삭제는 GPS 위치 기록만** (사용자 결정). `loc_events` 30일 그대로. 추억의 장소·일지·기록은 owner의 [어르신 데이터 지우기] 또는 마지막 사람이 빠질 때만 지운다.
4. **일지 알림:** 지금처럼 기기 단위 — 이번 범위 밖. (설계자 판단)
5. **범위:** 본선(11/22) 전에 최대한 다 넣는다 (사용자 결정). 만드는 순서는 시연 흐름 순 — 로그인 → 탭 → 추억의 장소 공유 → 초대 → 기억 꺼내기 대화 → 나머지. 단계마다 기존 기능 회귀 확인.

## 기억 꺼내기 대화 (사용자 결정: 넣는다)

📝 추억의 장소 탭. AI가 질문을 하나씩(옛 집·고향·옛 직장·자주 가던 시장·목욕탕·교회·병원 등 실종 어르신 발견 장소 유형 순), 보호자가 말로 답하면 장소 이름·근거를 뽑는다. `verify.js` 검사·⚠ 표시, 보호자가 확인한 것만 저장(source "memory", evidence에 대화 근거). 가족마다 따로 대화해도 같은 어르신 목록에 모인다. 서버 함수는 `/api/diary`에 mode 추가(`"memory"`). 프롬프트에 "없으면 null", "원문에 없는 사실 금지" 유지.

## 예상 경로 · 후보지 (사용자 결정: 예측해서 후보지를 만든다)

기존 "위치를 예측하지 않는다" 원칙을 바꾼다. `PRODUCT.md`(18·28행), `public/about.html`(26행), docs 결정표의 해당 문장도 함께 고친다.

1. **코드 — 예상 경로:** 당일 GPS의 마지막 위치·속도·진행 방향과 끊긴 뒤 지난 시간으로 시간대별 예상 위치와 지금 닿을 수 있는 범위를 계산(`public/lib/gps.js` 또는 새 규칙 모듈, 브라우저·서버 공용). 끊긴 이유 구분: 움직이다 끊김 / 멈춤 신호 뒤 조용함(그 자리 머묾).
2. **코드 — 후보 모으기:** 추억의 장소 + GPS 자주 머문 곳 + 예상 경로 위 기본 장소(공원·정류장 등, 기존 `BASIC_KINDS`). 후보마다 예상 위치까지 거리, 진행 방향과의 각도 차, 지금 닿을 수 있는지 계산.
3. **AI — 후보 고르기:** 후보 목록·계산값·장소 이야기(근거 문장)를 받아 가능성 높은 순서와 이유를 낸다. 서버 함수는 기존 파일에 mode 추가(어느 파일인지는 빌더).
4. **검증:** AI가 고른 곳이 2의 후보 목록에 없으면 버린다. 이유 문장의 숫자(거리·각도)는 코드 계산값과 대조, 다르면 ⚠.
5. **화면:** 📍 실시간 위치 탭과 🚨 실종자 찾기 요약 지도 — 후보지 1·2·3 + 이유 + 핀 + 예상 경로선 + 닿을 수 있는 범위.
6. **GPS가 없을 때:** 보호자가 말한 단서(나간 시각·방향·목적지)로 같은 흐름. **AI 실패 시:** 코드 계산(거리·방향) 순으로 후보를 보여 준다. (설계자 판단)

## 빌더에게 맡기는 것

- 탭을 한 HTML로 합칠지, 기존 HTML들에 공통 탭바를 붙일지 (기존 화면 코드를 최대한 그대로 쓰는 쪽).
- 동기화·인증 코드를 `public/js/common.js`에 둘지 새 모듈로 둘지.

- 서비스워커 버전 올리기.
